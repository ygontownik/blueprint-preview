What you don't have to do

~70% reuses scaffolding that already exists in proven production code. The architecture, the dashboard server, the action flow, the knowledge graph builder, the capture pipelines — all already-built patterns adapted to scale. The blueprint cites every leverage point.

🚫 Replace any existing system

ServiceNow stays ServiceNow. FOIAonline stays FOIAonline. The case management system stays. The dashboard sits on top of and reads from existing systems via MCP integrations. Nothing gets ripped out.

🚫 Train every staffer immediately

🚫 Bet the agency on this

How It Works

Seven stages, end to end. Each one explains what happens, in plain English, and why it matters. The whole pipeline runs in the background — most days, you don't think about it. You just open the dashboard.

1

Source materials come in

Every meeting recorded, every email received, every document filed, every Federal Register notice published, every OMB memo issued, every congressional letter sent — all of it flows into the capture surface. Some of it is captured automatically (meetings via Otter-equivalent, emails via Gmail/Exchange integration, Federal Register via API). Some is uploaded by staff.
Why it matters: if it isn't captured, it can't be analyzed. The blueprint requires every input modality to be wired in with classification-appropriate handling. No "I'll just keep that in my head" — that's how things slip.
2

Every item is triaged for quality, then extracted

Each captured artifact runs through two passes. First, a quality triage (Haiku, under 2 seconds): four dimensions scored — relevance to active programs (0–10), whether it requires a decision or action (0–10), whether it's already known / a duplicate (0–10), and how credible the source is (0–10). Items scoring below threshold go to a low-signal archive; they're not lost but they don't touch the dashboard. Items that pass go to extraction (Sonnet for transcripts, Opus for ambiguous cases): out comes structured data — actions with named owners and due dates, decisions with context, commitments with named counterparties, external intelligence with named programs it affects.
Why it matters: without quality triage, dashboards fill with low-value restates — every status meeting generates noise that dilutes signal. Without extraction, raw text is unusable. This stage converts noise into structured signal. The quality gate is what makes the dashboard trustworthy rather than overwhelming.
3

Everything gets routed to the right place — including peer programs

An action goes to the owner's queue, the program's action register, the relevant DR's dashboard, and (if it's inter-agency) the commitment tracker. Owner names get validated against the org's owner registry — typos and ambiguous attributions get flagged for review rather than silently misattributed. External intelligence gets matched to the programs it touches via the authority graph (a Federal Register notice on rule X appears on the dashboard of every program implementing rule X). And at this stage, the system also checks against the cross-program knowledge graph: does this situation resemble something another program has already navigated? If yes, a peer learning card is generated — "Program 14 handled a similar commitment slip with DOT last quarter by escalating two weeks early. It worked."
Why it matters: the same fact needs to appear everywhere someone might look for it — without manual duplication. And the cross-program matching means a program manager automatically benefits from every prior program's experience with the same counterparty or situation type. No one has to manually share knowledge. The system surfaces it.
4

The canonical state gets compiled

All the extracted, routed data gets written into one JSON file: blueprint-state.json. This file is the single source of truth for every dashboard, every briefing, every export. Before it's written, health checks run: schema validation (required fields present), owner whitelist check, past-due classification, tombstone respect (dismissed items stay dismissed).
Why it matters: "one canonical state, many surfaces" is the single most important architectural principle. If you let different views read from different sources, you get the "wait, which dashboard is right?" problem that plagues big orgs. This principle prevents that.
5

The dashboard server picks it up and caches it

A lightweight Python server (forked from the existing scaffolding) holds the canonical state in memory. When anyone hits any view — executive, per-DR, per-program, per-span function, portfolio, inter-agency, performance — the server hydrates the HTML from the cached state in milliseconds. PIV/CAC SSO gates access; the compile step has already masked any data the user shouldn't see for their role and classification level.
Why it matters: dashboard performance is what makes people actually use it. Sub-50ms refresh, no waiting, no spinners. And the role-based masking keeps things in compliance — a DR sees their span, not someone else's.
6

You and your team interact with it

You read briefings, drill into programs, resolve actions, dismiss outdated risks, answer open questions, sign off on decisions. Every interaction writes back to the canonical state. Dismissed items get tombstoned (they won't come back next compile). Resolved actions get classified (Resolved / Superseded / Stage-graduated / Rolled forward / Blocked) so the dashboard doesn't fill with stale items.
Why it matters: a dashboard that fills with stale items teaches you to ignore the dates. The tombstone-and-classification discipline keeps it trustworthy. When you see "12 actions overdue," you trust the number.
7

Information synthesizes differently for each level of the org

Every morning, three synthesis passes run against the same canonical state — each calibrated to a different resolution. At 6:30am, Haiku runs a per-program synthesis: full operational detail, all actions, all commitments, all peer learning cards, matched external intelligence. At 7:15am, Sonnet runs a per-DR synthesis: across their 3–5 programs, only exceptions — programs needing their attention, cross-program resource conflicts, commitments at risk in the next 14 days. At 7:45am, Opus runs the group-head brief: 3–5 signals only. No individual action items. No operational status. Exceptions, decisions, cross-cutting risks, and an external intelligence digest. Four minutes to read, cover to cover. The group head never sees a 40-item action queue. They see what needs their attention.
Why it matters: every large org fails in the same way — leadership either sees too much (100-item dashboards they learn to ignore) or too little (hand-curated summaries that hide problems). Hierarchical synthesis solves both. Detail stays at the level that can act on it. Signal rises to the level that needs to decide. Same data, different resolution — generated by a model calibrated to the decision needs of each role.
8

The system gets smarter — and shares what it learns across programs

Best practices from top-performing programs get extracted automatically (Opus reviews the last 90 days of logs, commitment completions, decision patterns) and proposed for promotion into the standard kit with a stable ID (BP-001, BP-002, etc.). But the system doesn't wait for a practice to be promoted before sharing it. The cross-program engine runs a nightly scan: for every program in a tagged situation type (commitment slipping, procurement delay, launch delay, etc.), it queries the knowledge graph for structurally similar programs that have faced the same situation. If it finds a match, it surfaces a specific, citable learning card to the program manager with source and outcome. At 6 months of operational history, the engine starts making pre-emptive pattern alerts — "Program 9's procurement approach matches the pattern that caused a 6-week delay for Program 2. Four weeks until their procurement action."
Why it matters: institutional knowledge in most orgs lives in people's heads and walks out the door. This system makes it accumulate in the codebase. Every program's resolved problem becomes the next program's early warning. Year 2 starts smarter than Year 1 ended — not because people remembered to share, but because the system is wired to surface it.

The two axes you'll see everywhere

The blueprint organizes work along two axes. Six vertical operating layers describe who does what work. Seven horizontal capability planes describe the shared infrastructure that supports every layer. See the Architecture tab for the 42-cell matrix.

Six layers — "who does what"
  1. L1 Executive Intelligence — you + your 6 DRs
  2. L2 Program Operations — program directors + teams
  3. L3 Span Functions — legal, finance, perf eval, comms
  4. L4 Cross-Program Intelligence — portfolio analytics
  5. L5 Inter-Agency Liaison — external coordination
  6. L6 Performance & Learning — continuous evaluation
Seven planes — "shared infrastructure"
  1. P1 Live Operational Dashboard — the UI
  2. P2 Universal Action Flow — actions everywhere
  3. P3 External Intelligence — what's happening outside
  4. P4 Context Architecture — memory + registries
  5. P5 Capture Surface — every input ingested
  6. P6 Synthesis & Briefing — multi-tier briefings
  7. P7 Knowledge Graph — people / programs / commitments linked
